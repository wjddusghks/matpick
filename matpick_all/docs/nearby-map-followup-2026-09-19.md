## 초기 로딩 용량

원본 자료의 병합·정리는 브라우저 실행에서 빌드 단계로 옮겼다. 즐겨찾기에서 식당 전체 데이터 대신 작은 ID 별칭 모듈만 읽어, 홈 진입 시 전체 식당 자료가 함께 내려오던 의존 관계를 끊었다.

공통 초기 묶음은 약 91% 줄었다. 이 수치는 빌드된 JavaScript 파일별 gzip 크기의 합계이며 실제 로딩 시간 측정값이 아니다. CSS·이미지·외부 API 요청은 포함하지 않는다. 지도 진입 시 식당 자료를 읽는 비용은 남아 있고, 전체 지도 묶음은 여전히 약 900KB다.

`scripts/check-bundle-size.mjs`는 홈이 전체 식당 자료를 정적으로 읽지 않는지 확인하고 공통 초기 200KB, 홈 300KB, 지도 1.1MB의 gzip 상한을 검사한다. 현재 측정값과 포함 파일은 `reports/bundle-size.json`에 기록한다.

## 데이터 갱신 절차

1. 원본 자료 또는 `client/src/data/restaurant-overrides.json`을 수정한다.
2. `pnpm data:check`로 공개 스냅샷 생성과 정합성 검사를 실행한다. ID 병합 규칙을 바꾼 경우 `pnpm data:aliases`도 실행한다.
3. `pnpm check`, `pnpm test`, `pnpm build`를 실행한다.
4. 생성된 `client/src/data/generated/public-dataset.json`, 별칭·리디렉션 변경, 사이트맵과 검사 보고서를 함께 반영한다.

`predev`와 `prebuild`는 공개 데이터와 별칭을 생성한다. `prebuild`는 정합성 검사와 SEO 파일 생성을 이어서 수행한다. `postbuild`는 용량 검사와 검색용 HTML 생성을 수행한다. 원본 병합은 `buildPublicDataset.ts`, 브라우저 질의는 `data/index.ts`가 담당한다. 테스트는 생성된 공개 스냅샷이 원본에서 다시 계산한 결과와 정확히 일치하는지도 검사한다.

## 지도 인증과 검증 한계

새 Maps 서비스의 `VITE_NAVER_MAP_KEY_ID`는 `ncpKeyId`로 전달한다. 기존 `VITE_NAVER_MAP_CLIENT_ID`는 기존 서비스용 `ncpClientId`를 유지한다. 둘 다 있으면 새 키 설정이 우선한다. 서로 다른 서비스의 키를 같은 것으로 취급하지 않는다. 근거는 [네이버 Maps 공식 시작 안내](https://navermaps.github.io/maps.js.ncp/docs/tutorial-2-Getting-Started.html)다.

2026-09-19에는 로컬 키의 지도 인증이 거부되었다. 2026-09-20에 사용자가 로그인한 네이버 콘솔의 `matpick` Maps 애플리케이션을 확인했다. 로컬에 사용하던 키가 현재 애플리케이션의 키와 달랐고, Web 서비스 URL에는 운영 도메인만 등록되어 있었다.

현재 애플리케이션의 공개 Client ID를 로컬 `.env.local`의 `VITE_NAVER_MAP_KEY_ID`에 설정하고, Web 서비스 URL에 `http://localhost:3000`을 추가했다. 기존 운영 주소는 유지했다. 키 재발급·Secret 변경은 하지 않았고 `.env.local`은 Git에서 제외되어 있다. 운영 호스팅 환경 변수에는 아직 적용하지 않았으므로 배포할 때 같은 Maps 애플리케이션의 공개 Client ID를 `VITE_NAVER_MAP_KEY_ID`로 지정해야 한다. 지도 오류 중에도 식당 목록과 외부 길찾기를 사용할 수 있다.

인증 수정 후 로컬 개발 화면에서 성수동 지도 배경, 식당 핀, 식당 선택 시 지도 초점·안내창을 확인했다. 모바일 390×844에서도 지도 핀들이 상단 검색창과 하단 추천 카드 사이에 표시되는 것을 확인했다. 실제 휴대폰 GPS 권한·위치 측정은 아직 별도 기기 검증 대상이다.
