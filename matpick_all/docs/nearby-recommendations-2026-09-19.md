# 보유 식당 정리 및 추천 지도 1차 구현

2026-09-19. ZIP 백업에서 복원한 로컬 개발본에 적용했다. 운영 서버에는 배포하지 않았다.

이 문서는 1차 작업 시점의 기록이다. 좌표 정정, 이전·폐업 반영, 로딩 용량 개선과 최종 검증 결과는 [2차 작업 기록](nearby-map-followup-2026-09-19.md)을 따른다.

## 반영한 1~5번

1. **식당 ID와 기존 주소 연결**: 현재 공개 식당 2,907곳의 대표 ID를 유지했다. 과거 ID 932개를 대표 ID로 연결하고 Vercel 영구 리디렉션 설정, 앱 내부 상세 연결, 즐겨찾기 참조 변환을 추가했다. 앱·사이트맵·검색용 HTML 생성은 같은 데이터 모듈을 사용한다. 같은 이름만으로 추가 병합하지 않았다.
2. **추천 근거**: 비어 있는 크리에이터 방문 기록 대신 실제 방송·가이드 출처를 센다. 동일 출처의 여러 회차는 보존하되 출처 수는 한 번만 센다. 기존 병합에서 사라졌던 회차를 보존하면서 출처 연결은 3,043건에서 4,295건으로 늘었다. 신규 식당을 추가한 수치가 아니다. 화면에는 ‘N개 출처에 소개’와 실제 출처명을 표시한다.
3. **좌표와 주변 추천**: 유효한 좌표의 후보를 직선거리순으로 정렬한다. 기본 1km부터 3·5·10·30km 순으로 범위를 넓혀 최소 3곳을 찾고 확대 사실을 안내한다. 30km 안에도 부족하면 가장 가까운 최대 3곳과 실제 범위를 표시한다. 목록은 처음 3곳, 더보기는 3곳씩이다. 지역 결과에 맞춘 지도 범위와 모바일 카드 공간을 조정했다. 위치 확인이 실패하면 동네·역 검색으로 계속할 수 있다.
4. **음식 분류와 운영 상태**: 빈 값·판단할 수 없는 음식 종류를 자동 한식으로 처리하지 않고 미분류로 둔다. 음식 원문은 카드에 유지한다. 미확인·영업 상태 확인·폐업·이전·휴업을 구분하고, 확인된 폐업·이전·휴업 식당은 추천 후보에서 제외한다. 기존 상세 주소에서는 상태 안내를 유지하고 이전 대상 연결을 지원한다. ‘영업 상태 확인’은 현재 시각의 영업시간 계산이 아니다.
5. **사진 없는 추천 카드**: 지도·탐색·공통 식당 카드에 식당명, 음식 종류, 거리(현재 위치를 사용하는 주변 탐색), 소개 근거, 주소, 길찾기, 공유, 상세 연결을 배치했다. 사진·메뉴 유무 때문에 빈 영역이 생기지 않는다. 길찾기는 동명 식당 혼동을 줄이도록 좌표를 사용한다.

## 데이터 확인 결과와 검토 대상

- 구조 검사: 식당 2,907곳, 출처 연결 4,295건, 별칭 932개, 오류 0건.
- 검토 묶음 87개: 같은 장소 ID 1묶음, 서울 지역 좌표 범위 6건, 같은 좌표 80묶음. 한 식당이 여러 묶음에 들어갈 수 있으므로 오류 식당 87곳이라는 뜻이 아니다.
- 음식 대분류 미분류 1,285건. 빈 값뿐 아니라 기존 분류 사전으로 확정할 수 없는 원문도 포함한다. 원문을 보존한 후 별도 보강할 수 있다.
- 같은 카카오 장소 ID를 쓰는 서울 동원집 두 주소는 이전인지 잘못된 매칭인지 확인되지 않아 보존했다.
- `reports/restaurant-data-check.json`에 식당별 검토 내용을, `reports/alias-review.json`에 대표 식당을 확정하지 못한 과거 기록을 남겼다. 후자의 기록에는 현재 비공개인 원본 데이터도 포함된다.
- 이번 작업에서 전 식당의 실제 위치·영업 상태를 새로 조사한 것은 아니다. `restaurant-overrides.json`은 빈 상태다.

## 앞으로 정보를 정정하는 위치

`client/src/data/restaurant-overrides.json`에서 대표 ID별 주소·좌표·음식 종류·운영 상태를 덮어쓸 수 있다. 원본 출처 파일을 보존하며 검토한 정정값만 적용하는 용도다.

운영 상태를 확정할 때는 `operationState`와 함께 `operationVerifiedAt`, `operationSourceUrl`을 기록한다. 이전한 새 식당이 별도 대표 ID로 존재하면 `replacementRestaurantId`를 연결한다. 상태의 허용 값은 `unknown`, `operating`, `closed`, `moved`, `temporarily_closed`다. 별칭을 수동으로 추가할 때는 최종 대표 ID로 직접 연결하고 순환·연쇄 연결을 만들지 않는다.

표준 개발 환경은 기존 프로젝트의 Node 22.x, pnpm 10.32.1을 유지했다. 이 PC에서 실제 검증한 실행 환경은 Node 24.19.0이며, 설치된 pnpm 11의 버전·저장소 차이를 피하기 위해 아래 스크립트와 도구 진입점을 직접 실행했다. lockfile과 프로젝트의 지정 버전은 변경하지 않았다.

```powershell
pnpm check
pnpm test
pnpm data:check
pnpm build
```

`prebuild`는 별칭 생성 → 데이터 검사 → 사이트맵 생성을 실행하고, `postbuild`는 검색용 HTML을 생성한다. 별칭 변경 시 생성된 `legacy-restaurant-aliases.json`과 저장소 루트의 `vercel.json`도 함께 반영해야 한다. 호스팅 설정은 배포 시작 시 읽힐 수 있으므로 빌드 중 변경에만 의존하지 않는다.

## 검증 범위와 배포 전 확인

- TypeScript 검사 및 회귀 테스트 8개 통과. 과거 배신식당 주소, 전체 식당 출처 수, 다른 주소의 동원집 보존, 음식 분류, 거리순·제외 상태·부족한 후보, 좌표 길찾기 URL, 사이트맵 식당 집합을 검사했다.
- Vite 배포용 빌드 및 식당 상세 HTML 2,907개 생성 완료. 생성된 상세 페이지의 대표 주소와 기존 주소 리디렉션 932개를 확인했다. 빌드 미리보기에서도 탐색 화면의 공통 추천 카드가 표시되는 것을 확인했다.
- 모바일 390×844에서 성수동 결과 11곳 중 처음 3곳, 더보기, 바로 보이는 길찾기 버튼, 위치 미확인 후 동네 검색 전환을 확인했다.
- 실제 과거 상세 주소가 대표 상세 주소로 전환되는 것을 브라우저에서 확인했다. Vercel의 HTTP 리디렉션은 배포 전이므로 설정과 대상으로 검사했다.
- 로컬 주소에서 네이버 지도 인증이 거부되어 **지도 배경·GPS를 포함한 전체 지도 사용성 검증은 끝나지 않았다**. 네이버 콘솔에서 개발 주소의 허용 도메인을 확인한 뒤 재검증해야 한다. 인증 오류·다운로드 시간 초과에는 목록을 계속 쓸 수 있는 안내를 표시한다. 인증 우회나 운영 콘솔 변경은 하지 않았다.
- 외부 길찾기 대상 URL과 좌표는 검증했다. 실제 경로와 소요시간 계산, 사용자 기기의 네이티브 공유 완료는 별도 기기 검증 대상이다.
- 빌드에는 약 9.48MB(압축 약 1.37MB)의 큰 초기 JavaScript 묶음 경고가 남아 있다. 데이터와 기능을 한 번에 읽는 구조가 있어, 다음 개발에서는 초기 지도 진입 속도 개선을 우선할 수 있다.

지도 인증 실패 처리는 [네이버 클라우드 공식 안내](https://www.ncloud-forums.com/topic/132/)의 콜백을 사용한다.
